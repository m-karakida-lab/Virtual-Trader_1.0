# ADR-004: 長期間データの再生・切替を「表示範囲だけ処理」「末尾だけ更新」「まとめ送り」で軽くする

## 状況
10年分の1分足（約375万行）で、1H・4Hなどの上位足パネルを含む3〜4画面の再生が20xでも遅く、パネル切替にも待ちがあった。実測（コード内の処理時間）で原因は3つ。
- オーバーレイ（足の抜き・雲・セッション帯・区切り線）が、表示範囲外も含む全期間を毎回走査していた（切替1回で`timeToCoordinate`約36万回）
- 非メインパネルが、再生の毎ステップで全期間の`setData`・指標の全再計算・区切り線/セッション帯の再計算をしていた
- lightweight-charts 4.2.3はデータ更新のたび、その系列の全点を再構築する（描画コストが系列本数×総本数に比例）

## 決定
1. 全期間を走査するオーバーレイは、`getVisibleLogicalRange`の範囲だけ処理する
2. 非メインは、確定足が前回と同じなら`computeTail`で末尾だけ`update()`する（それ以外は全体`setData`）。区切り線・セッション帯の元データは`nonMainCandles`にして毎ステップ再計算しない
3. 再生ループはフレームが間に合わない時、経過時間ぶん（最大30本）を`advance(steps)`でまとめて進める

## 理由
- 実測の改善: メイン切替（1H）1,176ms→240ms、`timeToCoordinate`36万回→約2万回、`priceToCoordinate`69万回→約1,000回。4画面（15m/1H/1H/1D）の再生1ステップ約670ms→約470ms
- 1Hメインの再生は、1ステップ約12ms、30本まとめて約38ms（描画を除く）。実機で「1Hでかなり速くなった」
- 捨てた案:
  - 系列に載せる本数を表示位置の周辺だけに絞る → 最も効くがスクロールのたびに再投入が要り、改修が大きい。必要になったら再検討
  - lightweight-charts v5へ更新 → 内部の改善が未確認でAPI変更が大きい
  - 描画のthrottle → 形成中足の更新が遅れて見える
- EMAは非表示（`visible:false`）の系列は描画コストがかからないため、使っていない指標の裏計算は軽微で放置

## 影響
- 新しいオーバーレイを足す時は、全期間を走査せず表示範囲だけ処理すること
- `computeTail`は全体計算（`computeEMA`等）の末尾と一致しなければならない（`indicators.test.ts`で検証）
- 残る主因はlightweight-chartsの全点再構築。長期間の細かい時間足パネルは今も重い。次の一手は系列本数の削減（上記の捨てた案の1つ目）
- ブラウザペインが非表示だとrAF・タイマーが止まり、時間の実測が歪む。測る時は表示させる
