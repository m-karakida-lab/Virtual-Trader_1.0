# ADR-005: 発注時のR:R画像はcanvasを直接重ね、DOMだけhtml-to-imageで描く

## 状況
TP/SL付きの発注時に、その時のチャート領域（R:R表示込み）を画像として取引に添付したい（トレード日誌用）。.vtdに埋め込むので容量を抑えつつ、細い線が潰れない画質も欲しい（希望: 100KB前後）。
既存のスクリーンショット機能（html-to-imageの`toJpeg`）をそのまま使うと、発注の瞬間に画面が1〜2秒固まった。実測では、`toCanvas`が約1,050ms（1600×900、HiDPI環境）。DOMだけなら約200msで、残りは1パネルに十数枚ある`<canvas>`を1枚ずつPNG化して再デコードする処理だった。

## 決定
- チャート領域は「canvasは`drawImage`で直接重ね（z-index順）、`<canvas>`を除いたDOMだけhtml-to-imageで描いて上に重ねる」方式で取り込む（`captureChartAreaCanvas`）
- 空（全面透明）のcanvasは、縮小プローブで中身が空かを調べて飛ばす
- 複数画面の区切り色（全面に敷かれた背景）は、撮影中だけ透明にして下に自前で塗る
- 画像の符号化（`encodeCanvasFitted`）は`toBlob`で非同期に行い、WebPの品質を二分探索して100KB以内に収める。収まらなければ縮小する
- 取り込みだけ発注前に行い（発注で下書きが消える）、符号化は発注後に裏で実行して`attachRrImage`で取引へ付ける

## 理由
- 取り込み時間: 約1,050ms→約190〜240ms。実機でも固まりが大きく減った
- 捨てた案:
  - html-to-imageのまま`skipFonts`だけ → ほぼ効果なし（支配的なのはcanvas）
  - `toDataURL`を縮小・空判定で差し替え → ほぼ効果なし（lightweight-chartsのcanvasは等倍で、空canvasは元から安い）
  - メインパネルだけを撮る → 速いが、上位足の環境認識が画像から消える
  - JPEG固定品質 → 容量が読めず、荒いか大きいかの二択になる
- WebPは同じ容量でJPEGより鮮明。品質を二分探索すると、上限（100KB）に近づけられる

## 影響
- DOM層（ラベル・ヘッダー・R:R箱など）は常にcanvasの上に重なる。元の重ね順（四角形が区切り線より上など）との差はごくわずか
- 撮影の瞬間、区切りの細い線の色が1フレーム抜ける（撮影後に復元）
- 高品質の縮小（`imageSmoothingQuality='high'`）は空canvas除外が前提。外すと再び遅くなる
- 指値が符号化の完了前に約定して建玉に変わると、その画像は付かない（まれ）
- 「キャプチャ」ボタンも同じ関数を使う（保存形式はWebP）
